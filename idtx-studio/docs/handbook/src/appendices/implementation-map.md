# Package compatibility and component map

Use this map to identify the component responsible for an authoring or delivery requirement. You do not need its engine implementation source. Keep Conductor, its bundled SDK and supplied target runtimes from compatible releases, and retain your distributor’s release information with your project.

| Component / contract | Where the developer gets it | What it enables / how to verify |
|---|---|---|
| Conductor executable/app | Complete authoring distribution | Project/level authoring, Behavior inspector, Preview and Build controls |
| Native libraries and USD resources | Kept in the distributed app layout | Startup, composition, schemas and resolver/plugins; confirm the app opens the example |
| Built-in player assets and behaviors | Supplied Conductor resources | Default desktop/XR player; confirm composed hierarchy and real controls |
| Behavior SDK workspace | Windows app-folder/behavior-sdk/idtx-behavior-sdk; macOS Contents/Resources/behavior-sdk/idtx-behavior-sdk | Public guest types, macros and ABI; Cargo Check uses this copy |
| Rust/Cargo and WASM target | Developer’s external Rust installation | Behavior compilation; check PATH and wasm32-unknown-unknown target |
| VS Code, rust-analyzer, `rust-src` and `rustfmt` | Developer’s editor/Rust installation; Inspector **Set up rust-analyzer** installs the extension in the selected profile | Completion, navigation, syntax/type diagnostics and checks on save |
| Managed behavior workspace | Generated by Inspector **Create Behavior…** or **Edit Code** under project `.idtx/behavior-ide/` | Connects author sources to Cargo, the matching SDK and WASM target; **Regenerate Editor Workspace** repairs it |
| Desktop Runtime | Supplied compatible host runtime | Out-of-process preview and finished desktop package |
| PCVR Runtime and OpenXR environment | Supplied PCVR-enabled runtime plus headset/platform software | Real XR preview and PCVR package; test device input/tracking |
| Quest runtime/resource tree | Supplied Android ARM64 runtime | Quest cook staging; Android SDK/JDK then assemble the APK |
| Vision Pro native runtime/resource tree | Supplied visionOS ARM64 device runtime | Device app packaging; macOS/Xcode/signing/device tools complete delivery |
| Optional net/remote/OpenExec/gesture support | Feature set compiled into supplied runtimes/resources | Relevant runtime operations; TOML requirements do not add native code |
| Project manifest, schema 1 | Authored project.toml | Registry, policy and cook configuration; [project reference](../composition/project.md) |
| Runtime manifest, schema 2 | Generated run.toml | Delivered entry/level registry, configuration and requirements; [cooking](../delivery/cooking.md) |
| Guest ABI, version 3 | SDK-generated WASM and supplied host | Import/layout compatibility; rebuild source with the matching SDK |
| Experience source files | Developer’s writable project directory | Portable USD/Rust/TOML; [complete example](../example/index.md) |
| Public API and coding-agent contract | This book | [SDK reference](../reference/behavior-sdk.md), [host contracts](../reference/behavior-host.md), [agent guide](../reference/agent-guide.md) |

ABI version alone does not identify additive API availability. An older ABI-3 SDK may lack a wrapper documented by this edition. Compile against the installed SDK and use the packager’s compatibility report for the supplied Runtime. A reported architecture/ABI/feature mismatch is a distribution mismatch; obtain the compatible components rather than modifying generated artifacts to bypass it.

This API edition includes composed relationship/curve snapshot imports, source-specific input and capture, source-aware widget processing, and playback status/release. Named clips also need the matching native USD/session controller and cook validation. Keep the updated SDK with the updated Conductor and Runtime; matching ABI 3 on older binaries does not establish availability of these additive imports. The public reference documents actual host behavior when it differs from a low-level SDK comment, including the requirement for nonempty playback labels.

A runtime capability grant, a project policy and compiled native support are separate requirements. For example, async HTTP needs the net grant, a permitted destination and runtime network support. A PCVR target needs its runtime and actual OpenXR backend. An editor control being visible does not establish every target’s hardware or external signing tool.

## Distribution acceptance

A developer can check a new authoring distribution without an engine checkout:

1. Open the portable example in Conductor and inspect both levels.
2. Confirm the SDK is present. Use the Inspector’s **Edit Code** action to open the managed workspace, confirm rust-analyzer completion/diagnostics, save files and run Cargo Check/Verify capabilities on the bindings.
3. Launch Desktop preview and verify player input, beacon and console.
4. Build Desktop Experience and confirm a finished package is produced.
5. Run Hub → Lab → Hub and relocate the complete package.
6. Repeat relevant Build/install checks for every advertised target runtime.

Report the distribution identity, missing component or compatibility message and the smallest failing step to the supplier. The [validation record](validation.md) describes which book checks have actually been performed.
